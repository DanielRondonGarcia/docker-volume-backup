# Native Worker Installers and Enrollment

## Objective

Add downloadable native worker packages for Linux and Windows, published as GitHub Release assets and offered from the Control Plane worker-enrollment flow, with safe first-run enrollment and no bootstrap secret in public artifacts.

## User-approved direction

- Add a **Worker nativo** option alongside the existing Docker Compose enrollment instructions.
- Publish generic Linux amd64 and arm64 `.deb` packages and a Windows x64 `.exe` worker artifact as versioned GitHub Release assets; the Control Plane links to the latest stable compatible release and shows version/checksum metadata.
- Keep artifacts generic/reusable. Never embed a per-worker enrollment token or credential in a package, installer, release asset, command argument, or public config template.
- At first enrollment, the worker receives a short-lived one-use token out-of-band (secure interactive prompt by default), generates a separate per-worker durable credential, and stores only the durable credential locally after successful enrollment. The token is removed/not persisted after use.
- Introduce a versioned, retry-safe enrollment path for new native clients while retaining the existing V1 behavior for already-installed workers.
- Build the Windows output as a portable console worker executable and use Task Scheduler guidance for background startup; do not claim Windows SCM service or introduce an unrequested service wrapper. Linux `.deb` installs a worker executable and systemd unit, but does not start an unenrolled agent.
- Build Linux amd64 and arm64 PyInstaller outputs on native runners using the oldest supported glibc baseline (`manylinux2014`, glibc 2.17); build Windows x64 on a Windows runner. Package only the Vaultline worker code/runtime; external backup executables (`restic`, `tar`, `gpg`, `rclone`, `aws`, `ssh`, `scp`) remain separately installed and feature-dependent.

## Security and protocol decisions

- The current enrollment token is one-use server-side but becomes the durable HMAC secret. Replace this for new native package enrollment with a distinct worker credential generated by the client.
- Make V2 completion idempotent for the exact same enrollment token digest, attempt ID, and credential digest, so a lost HTTP response can be retried without allowing a different key to claim the consumed token.
- Keep the existing V1 endpoint and credential path for legacy workers. Do not silently downgrade a V2 request after a network error; fallback, if any, is only for a positively identified unsupported endpoint and must be explicit in code/tests.
- Persist a pending client credential/attempt before sending completion so a process restart can retry with the same attempt ID/key. Prompt for the bootstrap token on the terminal without echo; never accept it as a command-line argument. Remove pending bootstrap material after success.
- The Control Plane continues to store only the existing digest/signing-equivalent verifier for durable HMAC credentials; a broader HMAC database-at-rest redesign is explicitly out of scope and should not be represented as solved here.
- Release assets will include SHA-256 checksums. No Authenticode signing certificate or signing secret is currently configured; do not claim the Windows executable is signed, and document that Windows may show an unsigned-binary warning.

## Compatibility / non-goals

- Preserve Docker Compose worker enrollment and all existing V1 workers.
- Do not rename the GitHub repository, existing GHCR/Docker Hub images, deployment labels, environment contracts, compose/Kubernetes identifiers, or old config/state paths.
- No auto-update daemon, package repository, MSI wizard, Windows SCM service, or automatic installation of third-party backup executables.
- No push, PR, merge, or manually triggered release without separate user authorization.
- Preserve pre-existing `.atl/`, tracked `__pycache__`, `.codegraph/`, `.playwright-mcp/`, and both previous feature task-record changes.
